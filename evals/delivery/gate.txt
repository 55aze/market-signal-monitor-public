- Before choosing signals, read BOTH Packet and persisted Delivered IDs completely from the configured report row, even if prior chat history is unavailable. A successful, explicitly empty property is empty; unreadable, truncated, malformed or schema-mismatched receipt data is RECEIPT_READ_FAILED, never empty.
- Validate a structured persisted receipt using the backend contract: item_ids are strings, packet_id equals identity("packet", sorted(unique(item_ids))), explicit delivered_at is present, and unknown time requires delivery_evidence=prior_complete_report. identity is the first 24 hex characters of SHA256 of Python json.dumps(parts, sort_keys=True), including its default spaces. Validate any non-null time as timezone-aware, not future. Legacy ID arrays/CSV can suppress their exact IDs as the backend supports, but do not invent a delivery timestamp or promote them to a structured receipt. If validation cannot be completed, report RECEIPT_READ_FAILED and stop signal delivery.
- A valid persisted receipt is durable evidence for excluding its IDs; it does not require recovering the old chat again. Do not overwrite an existing receipt with an older or different prior-chat receipt while any persisted receipt IDs still occur in the current Packet. Preserve pending receipt evidence until the producer consumes it.
- Verify the whole Packet's version, fields, unique IDs, count and end marker BEFORE suppression. Do not hide a truncated Packet behind matching IDs.
- If every Packet item is covered by persisted receipt IDs or by an actually readable COMPLETE prior report, emit no new signals and no new Receipt. Operational changes may still be reported. A failed acknowledgement write must emit WRITE_FAILED, while known prior-reported IDs remain excluded.
- If only some Packet items are covered, do not emit a partial batch or fabricate a subset Receipt using the original packet_id. Return one line ACK_PENDING: 已确认信号仍在当前批次，等待扫描器生成未播批次. Leave persisted receipt unchanged. The next producer scan should remove acknowledged IDs; if it does not, this remains an operational failure, not successful delivery.
- If no overlap remains, follow the existing full-report and exact Receipt rules. A complete prior report may be acknowledged only without losing unconsumed persisted receipt evidence; perform exact readback after writing.
- If prior history is unavailable AND Delivered IDs is empty, delivery status cannot be distinguished from a first-ever run. Emit DELIVERY_UNCONFIRMED and no signals/Receipt, unless explicit first-delivery authorization or a durable first-run marker establishes that no earlier report exists. Never infer first run from an empty receipt. With explicit first-delivery authorization, report the full validated Packet; do not acknowledge the current response.
- This gate does not supply an atomic display callback or solve concurrent reporters. Do not claim exactly-once delivery or mark uncertain reports delivered.
